# ТЗ: интеграция канбан-доски с кодинг-агентами по ACP

Версия 0.2 — редакция под Wails (заменяет 0.1)

---

## 0. Что изменилось относительно v0.1

| | v0.1 (внешний мост) | v0.2 (Wails) |
|---|---|---|
| Язык интеграции | Python | **Go** |
| Развёртывание | отдельный сервис + HTTP | **один процесс**, отдельный Go-пакет |
| Источник событий | WebSocket / `webhook_update` | внутренняя подписка на события доски |
| Разрешения агента | allow-list с автоотказом | **модальное окно пользователю** |
| Вывод агента | комментарии на карточке | **стриминг в UI**, итог — в карточку |
| Лицензия | AGPL не затрагивается | **AGPL применяется полностью** |

Причина смены языка: приложение целиком на Go, а SDK для ACP на Go существует (`coder/acp-go-sdk`, есть `SpawnAgent`, пример клиента и пример моста к Claude Code). Запускать Python-сайдкар из Go-процесса ради спавна ещё одного subprocess нецелесообразно.

---

## 1. Цель

При переходе карточки в заданную колонку автоматически запускать сессию кодинг-агента по ACP, показывать ход работы в реальном времени в интерфейсе приложения и фиксировать итог на карточке.

**Протокол:** Agent Client Protocol — JSON-RPC 2.0, newline-delimited поверх stdio. Агент запускается как дочерний процесс. Одно соединение обслуживает несколько параллельных сессий.

### 1.1. Вне текущего этапа

- Удалённые ACP-агенты (HTTP/SSE-транспорт) — в SDK заявлен, но агенты в экосистеме пока локальные.
- Многопользовательский режим: приложение десктопное, single-user.
- Автоматический коммит/пуш результатов работы агента.

## 2. Архитектура

Одно Wails-приложение, один процесс.

```
┌──────────────────────── Wails App (Go) ────────────────────────┐
│                                                                 │
│  frontend (React, webview)                                      │
│      ▲  EventsEmit: acp:chunk, acp:tool, acp:permission         │
│      │  bindings:   StartSession, CancelSession, AnswerPermission│
│      ▼                                                          │
│  app.go — слой биндингов, не содержит логики                    │
│      │                                                          │
│  internal/acp/                                                  │
│      manager.go  — сессии, лимиты, очередь, отмена              │
│      client.go   — реализация acp.Client: permissions, fs/*     │
│      trigger.go  — подписка на события доски, диффер, дедуп     │
│      │ stdio (JSON-RPC)                                         │
│      ▼                                                          │
│  ACP-агент (дочерний процесс)                                   │
│                                                                 │
│  internal/board/ — сервер Focalboard, запущен in-process        │
└─────────────────────────────────────────────────────────────────┘
```

### 2.1. Принцип изоляции

Пакет `internal/acp` **не импортирует внутренности сервера доски**. Он знает только про интерфейс:

```go
type BoardEvents interface {
    Subscribe(ctx context.Context) (<-chan CardMoved, error)
}

type BoardWriter interface {
    AddComment(ctx context.Context, cardID, text string) error
    MoveCard(ctx context.Context, cardID, columnID string) error
}
```

При последующем переезде на собственный бэкенд меняются только реализации этих двух интерфейсов, логика ACP не трогается.

**Запрещено** размещать код ACP внутри `server/` Focalboard.

## 3. Источник событий: выбрать в Фазе 0

Три варианта по возрастанию связанности с кодом доски:

1. **WebSocket на localhost** — работает без изменений в сервере, нулевая связанность. Нелепо внутри одного процесса, но пригодно как временное решение Фазы 1.
2. **Регистрация своего `notify.Backend`** — у Focalboard есть подсистема `server/services/notify` с интерфейсом бэкендов, передаваемых в параметры сервера. Штатная точка расширения, а не патч ядра. **Целевой вариант.**
3. **Обёртка слоя app/store** при инициализации в собственном `main.go`.

**Задача Фазы 0:** проверить, экспортирована ли регистрация notify-бэкендов в публичном API конструктора сервера. Если да — идём вторым путём.

### 3.1. Детект перемещения

В Focalboard колонка — не сущность, а опция select-свойства карточки. Перемещение = патч, в котором изменилось `fields.properties[statusPropertyId]`.

Событие не всегда содержит прежнее значение, поэтому `trigger.go` хранит последнее известное состояние карточек. Состояние персистентное (SQLite рядом с базой доски), чтобы диффер корректно работал после перезапуска приложения.

Нормализованное событие:

```go
type CardMoved struct {
    EventID    string
    CardID     string
    BoardID    string
    Title      string
    Body       string
    Props      map[string]string // включая repo_path, branch
    FromColumn Column
    ToColumn   Column
    At         time.Time
}
```

## 4. Жизненный цикл ACP

### 4.1. Соединение

Одно на процесс агента, а не на карточку. Установка при первом обращении, переиспользование далее.

```
initialize {protocolVersion, clientCapabilities: {fs: {readTextFile, writeTextFile}}}
  → ответ с capabilities агента
```

Менеджер обязан **адаптировать поведение под фактически заявленные агентом capabilities**, а не предполагать полный набор.

### 4.2. Сессия

```
session/new    {cwd: "<абсолютный путь>", mcpServers: []}  → sessionId
session/prompt {sessionId, prompt: [{type: "text", text: "<задача>"}]}
  → поток нотификаций session/update
```

`cwd` обязан быть абсолютным. Источник — свойство карточки `repo_path`, валидируется по белому списку корней из конфига. Пустой, несуществующий или выходящий за белый список путь → сессия не запускается, на карточку пишется понятная ошибка.

### 4.3. Обработка `session/update`

| Тип | Куда |
|---|---|
| `agent_message_chunk` | `EventsEmit("acp:chunk")` в UI + буфер для итога |
| `agent_thought_chunk` | только в лог сессии, в UI по флагу «показывать размышления» |
| `tool_call`, `tool_call_update` | `EventsEmit("acp:tool")` — строка в панели выполнения |

Итоговое сообщение по завершении — комментарием на карточке (см. п. 7).

## 5. Интерактив: главное преимущество Wails

### 5.1. Запросы разрешений

В headless-схеме v0.1 `session/request_permission` был тупиком: ответить некому, сессия висит. Здесь запрос доводится до пользователя.

Протокол:

```
агент → client.RequestPermission(req)
      → runtime.EventsEmit("acp:permission", {requestID, sessionID, cardID, tool, args})
      → фронтенд показывает модалку
      → биндинг AnswerPermission(requestID, decision)
      → менеджер разблокирует ожидающую горутину, отвечает агенту
```

Требования:
- Ответ доставляется через канал, зарегистрированный по `requestID`; горутина сессии ждёт на нём с таймаутом.
- **Таймаут обязателен** (по умолчанию 5 мин): если пользователь ушёл от компьютера, сессия должна завершиться отказом, а не висеть вечно.
- Опция «всегда разрешать этот инструмент в этой сессии» — сохраняется в памяти сессии, не глобально.
- Конфигурируемый allow-list для инструментов, не требующих подтверждения (например, чтение файлов).

### 5.2. Файловые операции

Если объявлены `fs.readTextFile` / `fs.writeTextFile`, менеджер обязан их обслуживать. Запись ограничена пределами `cwd` сессии; попытка выйти за пределы — ошибка в ответе агенту и запись в лог.

## 6. Состояние (SQLite)

```sql
card_state(card_id PK, board_id, column_id, updated_at)

agent_session(
    id PK, card_id, agent_kind, acp_session_id,
    status,          -- queued|running|waiting_permission|done|failed|cancelled
    cwd, started_at, finished_at, error_text)

session_event(id PK, session_id, seq, kind, payload_json, created_at)

idempotency(key PK, session_id, created_at)
```

`session_event` нужен, чтобы при повторном открытии карточки показать в панели прошлый ход работы, а не пустоту.

## 7. Обязательные политики

| Проблема | Требование |
|---|---|
| Drag-n-drop даёт серию патчей | Идемпотентный ключ `card_id + from + to + окно 10 с`. Одно перемещение = максимум одна сессия |
| Агент завис | Таймаут сессии (по умолчанию 15 мин) → `session/cancel` → статус `failed` |
| Карточку вернули назад во время работы | Активная сессия отменяется |
| Параллелизм | Лимит одновременных сессий (конфиг, по умолчанию 3), сверх лимита — очередь со статусом `queued` |
| Агент упал | Перезапуск процесса, все его сессии → `failed`, комментарий на карточках |
| Затирание правок человека | Писать **только комментариями**, никогда не в описание карточки |
| Два агента в одном репозитории | Либо запрет параллельных сессий на один `cwd`, либо git worktree на сессию (см. п. 11) |

## 8. Особенности Wails

- **Не блокировать UI-поток.** Каждая сессия — отдельная горутина. Биндинг `StartSession` только ставит задачу и сразу возвращает `sessionId`.
- **Push только через `runtime.EventsEmit`.** Не пытаться возвращать поток из биндинга — семантика биндингов синхронная.
- **Осиротевшие процессы.** При закрытии окна приложение завершается, но дочерние агенты могут пережить его. Требуется `context.WithCancel` уровня приложения плюс явное убийство process group в `OnShutdown`. Проверяется отдельным тестом.
- **Версия Wails.** Зафиксировать v2 или v3 до начала работ — структура проекта и API рантайма различаются; на момент составления ТЗ v3 был заметно менее зрелым. Уточнить актуальный статус.
- **Единый бинарь.** Агент (`claude`, `gemini` и т.п.) в бинарь не входит — это внешняя зависимость. Нужна проверка наличия при старте и внятное сообщение, если не найден.

1. Поднять Focalboard локально, убедиться, что сервер стартует in-process из своего `main.go`.

4. **Зафиксировать фактические сигнатуры и версию протокола** — спецификация активно меняется, сверять с `agentclientprotocol.com` на момент разработки.

**Готово, когда:** есть Go-скрипт, запускающий агента по хардкоженному промпту и печатающий стриминг в консоль.

Wails-оболочка вокруг Focalboard, подписка на события, запуск сессии, стриминг в панель UI.

**Готово, когда:** перетаскивание карточки в колонку «To Agent» открывает панель с живым выводом агента.

### Фаза 2. Интерактив и надёжность (2 недели)

Модалка разрешений, отмена, таймауты, идемпотентность, очередь, персистентность, корректный shutdown.

### Фаза 3. Отвязка от Focalboard

Замена реализаций `BoardEvents` / `BoardWriter` на собственный бэкенд. Пакет `internal/acp` не меняется.

## 10. Критерии приёмки

**Фаза 1**
1. Перемещение в триггерную колонку создаёт ровно одну сессию; в нетриггерную — ни одной.
2. Вывод агента виден в UI в реальном времени.
3. Пустой или невалидный `repo_path` даёт понятную ошибку, а не зависание.

**Фаза 2**
4. Пятикратное быстрое перетаскивание туда-обратно не порождает более одной сессии.
5. Запрос разрешения показывает модалку; отсутствие ответа 5 минут завершает сессию отказом.
6. Отмена с карточки останавливает агента в течение 2 секунд.
7. Перезапуск приложения не ломает диффер и показывает прошлый лог сессии на карточке.
8. Закрытие окна не оставляет живых процессов агента (проверяется в тесте).
9. Убийство процесса агента извне переводит сессии в `failed` с комментарием.

## 11. Открытые вопросы

1. **Основной агент** — от него зависят аргументы запуска. Реализовано: именованный реестр агентов (`kind: claude|codex`) с выбором по полю карточки "Agent". ⚠️ У Codex **нет** ACP-режима (`codex acp` не существует) — вместо этого используется `codex exec --json` через чистый Go-мост `internal/acp/codexbridge` (аналог `claudebridge`). Изоляция нескольких агентов/аккаунтов — через per-process `env` (`CODEX_HOME`/`OPENAI_API_KEY`, `CLAUDE_CONFIG_DIR`/`ANTHROPIC_API_KEY`), без изоляции терминалов.
2. **Один процесс агента на всё или на репозиторий?** Второе изолирует лучше, но дороже по памяти.
3. **Изоляция рабочей копии.** Агент пишет прямо в рабочий каталог или в отдельный git worktree на сессию? Второе снимает конфликты при параллельных сессиях, но усложняет доставку результата.
4. **Ручной запуск.** Нужна ли кнопка «запустить агента» на карточке помимо автотриггера по колонке.
5. **Ревью результата.** Двигать карточку дальше по доске автоматически при успехе или всегда оставлять решение человеку?
6. **Версия Wails** (v2/v3) — зафиксировать до старта Фазы 1.

## 12. Лицензионное ограничение

Миграция Focalboard на Wails — это модифицированная версия, собираемая из исходников. **Действует AGPL v3, включая сетевой копилефт.** Исключение по MIT распространяется только на бинарники, выпущенные самой Mattermost, Inc.; отдельные каталоги (`server/model/`, `config.json`, `webapp/i18n/` и др.) — Apache 2.0.

Практически это означает: при распространении приложения вы обязаны предоставлять исходный код производной работы на условиях AGPL. Для внутреннего инструмента или открытого проекта это приемлемо. **Для закрытого коммерческого продукта данная схема не подходит** — там требуется собственный бэкенд, а от Focalboard берутся только идеи и Apache-компоненты.

Это не юридическая консультация. Лицензия Mattermost составлена нестандартно; перед публичным релизом требуется проверка юристом либо запрос в `commercial@mattermost.com`.
