# Как выпускается версия

Релиз — это тег. Всё остальное делает `.github/workflows/release.yml`: собирает
четыре платформы нативно, подписывает манифест обновления и выкладывает всё в
бакет, откуда приложение и качает.

Пользовательская половина — что человек видит в приложении — описана в
[руководстве](guide/settings/updates.md). Здесь только выпуск.

## Репозиторий закрытый, и ничему здесь это не мешает

Ничего из выпуска не требует публичного репозитория. Actions работают в
приватном; наружу уезжают только собранные файлы, и уезжают они в S3-совместимый
бакет под нашим доменом.

Разделение, ради которого выбран провайдер `endpoint`:

- **Манифест — `https://updates.deffun.com/stable.json`**, и это единственный
  адрес, который **нельзя поменять**: каждая установленная копия спрашивает
  здесь и больше нигде. Поэтому он и на своём домене — куда указывает домен,
  решается заново хоть каждый выпуск.
- **Файлы — по версионному пути в том же бакете**
  (`https://updates.deffun.com/v1.1.0/…`), и ссылки на них внутри манифеста
  абсолютные. Переехать в другое хранилище — это поменять, куда смотрит домен, и
  выпустить следующий манифест. Установленные приложения ничего не заметят.

Адрес написан ровно в одном месте — `updateManifestURL` в `updates.go`.
Workflow читает его оттуда же и строит из него путь выпуска, чтобы приложение и
релиз не могли разойтись во мнениях о том, где живёт выпуск.

## Один раз: бакет

Подойдёт любое S3-совместимое хранилище — Cloudflare R2, Backblaze B2, обычный
S3. Нужно:

1. Бакет с **публичным чтением** и своим доменом `updates.deffun.com`
   (в R2 это Settings → Public access → Custom domain; домен должен быть в
   Cloudflare DNS; в B2 — публичный бакет плюс CNAME через Cloudflare).
2. Ключ доступа с правом записи в этот бакет.
3. Четыре секрета репозитория:

   | Секрет | Пример |
   |---|---|
   | `RELEASES_S3_ENDPOINT` | `https://<account>.r2.cloudflarestorage.com` |
   | `RELEASES_S3_BUCKET` | `xciii-releases` |
   | `RELEASES_S3_ACCESS_KEY_ID` | |
   | `RELEASES_S3_SECRET_ACCESS_KEY` | |

Раскладка в бакете после выпуска:

```
stable.json                                  ← манифест, перезаписывается
v1.1.0/XCIII-1.1.0-darwin-arm64.zip          ← обновление
v1.1.0/XCIII-1.1.0-darwin-arm64.dmg          ← первая установка
v1.1.0/…
```

Заголовки кэша выставляет workflow: файлы под версионным путём неизменны и
кэшируются навсегда, `stable.json` — на пять минут. Манифест, закэшированный на
сутки, — это выпуск, которого сутки никто не видит.

## Один раз: ключ подписи

Обновление ставится, только если сходится с ключом, вшитым в бинарник. Пара уже
создана:

- `build/updater.key.pub` — открытая половина, лежит в репозитории и попадает в
  каждый бинарник через `//go:embed` в `updates.go`;
- `build/updater.key` — закрытая. В репозиторий она не попадает
  (`.gitignore`), и её нужно положить в секрет репозитория
  **`UPDATER_PRIVATE_KEY`** целиком, вместе со строками `-----BEGIN …-----`.

Кто держит закрытый ключ, тот может выпустить обновление любому пользователю.
Хранить как сертификат подписи кода: менеджер паролей плюс секрет CI, и больше
нигде.

Сменить пару — `wails3 updater genkey -out build/updater.key -force`, закоммитить
новый `.pub`, обновить секрет. Пользователи со старой версией после этого
обновиться **не смогут**: они проверяют подпись прежним ключом. Смена ключа —
это ручная переустановка для всех.

## Каждый раз: выпуск

```
wails3 task version:set VERSION=1.1.0
go test .                       # версия должна сойтись во всех файлах
git commit -am "Release 1.1.0"
git tag -a v1.1.0               # текст аннотации станет заметками к выпуску
git push && git push --tags
```

`version:set` пишет номер в `version.go`, `build/config.yml` и в
per-platform сборочные файлы — список в `internal/buildversion`.
`version_test.go` падает, если они разошлись; тот же номер проверяет и workflow,
сверяя его с тегом.

**Аннотация тега — это то, что прочитает пользователь.** Она попадает в манифест
и оттуда в панель «Обновления» в приложении. Markdown; лёгкий тег (без `-a`)
оставит выпуск с одним номером версии.

## Что собирается

| Раннер | Обновление (`dist/update/`) | Первая установка (`dist/install/`) |
|---|---|---|
| macos-14 | `XCIII-<v>-darwin-arm64.zip` | `.dmg` |
| macos-13 | `XCIII-<v>-darwin-amd64.zip` | `.dmg` |
| windows-latest | `XCIII-<v>-windows-amd64.exe` | `-installer.exe` (NSIS, `INSTALL_SCOPE=user`) |
| ubuntu-latest | `XCIII-<v>-linux-amd64.tar.gz` | AppImage, `.deb` |

Деление на две папки — не косметика: `manifest.json` строится только по
`dist/update/`, и попавший туда инсталлятор апдейтер поставил бы **вместо**
приложения.

macOS-архив делается `ditto -c -k --keepParent`, а не `zip -r`: `.app` — это
бандл с симлинками и расширенными атрибутами, и `zip` молча теряет и то, и
другое.

Сборка нативная на каждой платформе, потому что иначе нельзя:
cgo-SQLite, `makensis` и `ldd` — см.
[build-and-platforms.md](build-and-platforms.md).

## Как это проверяет само себя

Четыре проверки в workflow:

1. **Тег против дерева.** `v1.1.0` при `appVersion = "1.0.0"` — это выпуск,
   который вечно предлагает всем обновиться до уже установленной версии.
2. **`wails3 updater manifest`** считает SHA-512 каждого артефакта и подписывает
   его закрытым ключом.
3. **`wails3 updater verify -publickey build/updater.key.pub`** — против
   *закоммиченного* открытого ключа, то есть против того самого, который вшит в
   собранные бинарники. Расхождение здесь — это обновление, которое никто не
   смог бы поставить.
4. **После публикации — чтение фида так, как его читает приложение**: `curl` по
   адресу из `updateManifestURL`, проверка подписи скачанного манифеста и `HEAD`
   на каждую ссылку в нём. Бакет без публичного доступа или с неподключённым
   доменом падает здесь, а не у человека в приложении.

Порядок выкладки — сначала файлы, потом манифест. Манифест и есть объявление о
том, что выпуск существует; выложенный первым, он открывает окно, в котором
приложения качают 404 и показывают неудачное обновление совершенно исправного
выпуска.

## Проверить workflow, не выпуская ничего

`workflow_dispatch` с `dry_run` (по умолчанию включён): собирает всё, подписывает
манифест, печатает его и **ничего не выкладывает**. Первый настоящий тег не
должен быть первым запуском workflow.

## Первый выпуск

Приложение сравнивает версии по SemVer, поэтому первый выпуск должен быть строго
новее того, что уже стоит у людей. Сейчас в дереве `1.0.0` и выпусков нет —
значит первый тег либо `v1.0.1`, либо `version:set VERSION=0.1.0` и дальше с
нуля.

## Чего в этом ещё нет

- **Подписи Apple и Windows.** Задачи `darwin:sign:notarize`, `windows:sign` и
  `windows:sign:installer` в Taskfile есть, сертификатов нет, в workflow эти шаги
  не вызываются. Пока приложение подписано ad-hoc, и после подмены macOS
  переспросит про запуск — ровно как при первой установке.
- **Каналы.** Один канал, `stable`. Второй манифест (`beta.json`) в том же
  бакете — это одна строка в workflow; чего нет, так это переключателя в
  приложении, и мешает этому `Init`, который вызывается один раз за запуск. См.
  [deferred.md](deferred.md).
- **Страница загрузки.** Файлы лежат в бакете, но `site/xciii/` про них ещё не
  знает: там форма предзаказа. Ссылки вида
  `https://updates.deffun.com/v1.1.0/XCIII-1.1.0-darwin-arm64.dmg` можно ставить
  на страницу руками, пока не появится что-то, что читает `stable.json`.
- **Прогон тестов в релизном workflow.** Сейчас его нет: тег вешают на то, что
  уже проверено локально.
