# Ревью схем БД

Дата: 2026-08-12. Повод — обсуждение типовых ошибок ИИ-генерированных схем;
исходный reddit-пост оказался недоступен, поэтому ревью шло по стандартному
чеклисту жанра: индексы под реальные запросы, PK/UNIQUE, типы, NOT NULL,
ретеншн, версионирование схемы, атомарность записи.

Принятые решения: **правки не применяются** (это отчёт, а не патч);
**ретеншн в acp.db не вводится** — журналы там оставлены расти сознательно.

БД три:

1. **xciii.db** — бордовая, `server/services/store/sqlstore/migrations/`:
   40 миграций, все апстримные Focalboard. Локальных DDL-правок нет — весь
   sqlstore пришёл одним коммитом (1e49a02), дальше менялся только Go-код.
2. **acp.db** — `internal/acp/store.go`: сессии агентов, их события,
   терминалы, позиция карточек на маршрутах, очередь стадий, идемпотентность,
   `vcs_seen`, `board_setup`.
3. **sources.db** — `internal/sources/store.go`: дедуп входящих и журнал
   решений источников.

Общий вердикт: серьёзных ошибок «ИИ-жанра» (даты строками, JSON вместо связей,
отсутствие NOT NULL, бессмысленные суррогатные ключи) в наших схемах нет.
Типы единообразные (unix-ms в INTEGER), естественные PK, upsert'ы через
ON CONFLICT, WAL. Находки точечные, и самая весомая — апстримная.

## Основная БД (xciii.db)

1. **`file_info` — без PK и без единого индекса.** Миграция `000017` создаёт
   таблицу с голым `id varchar(26) NOT NULL`, и каждый запрос файла
   (`sqlstore/file.go`, `WHERE id=?`) — полный скан. Единственное место,
   которое будет заметно деградировать с ростом вложений. Лечение — локальная
   миграция `000041`:
   `CREATE UNIQUE INDEX IF NOT EXISTS idx_file_info_id ON file_info(id);`
2. **SQLite молча потерял `idx_category_boards_category_id`.** `000020` его
   создаёт, а SQLite-ветка `000036` пересобирает таблицу (RENAME → CREATE →
   INSERT → DROP) ради UNIQUE-констрейнта и индекс не восстанавливает —
   Postgres/MySQL-ветка идёт через `addConstraintIfNeeded` и индекс сохраняет.
   Запросы по `category_id` в коде есть (`category_boards.go:43,152,174`).
   Восстановить той же миграцией 000041; `//go:embed migrations/*.sql` новые
   файлы подхватит, golang-migrate докатит существующие БД.
3. **Бордовая БД — единственная из трёх без прагм**: `server.go` передаёт
   голый путь, то есть rollback journal и без busy_timeout; живёт это за счёт
   `SetMaxOpenConns(1)` (`server/server/server.go`). Наши БД открываются с
   `?_busy_timeout=5000&_journal_mode=WAL` — та же строка напрашивается и
   здесь (journal_mode=WAL персистентен, одной установки хватает).
4. Что **не** предлагается трогать в несённом форке: отсутствие FK (апстримный
   стиль — soft-delete и `*_history`-таблицы, FK туда не ложатся), рудименты
   `workspace_id` в sharing/subscriptions/notification_hints, пустую `teams`.
   Правки в форк должны оставаться маленькими и объяснимыми.

## acp.db

Хорошее: единый формат времени, NOT NULL + DEFAULT всюду, естественные PK,
upsert'ы, WAL + busy_timeout, индексы совпадают с запросами.

1. **Ретеншна нет** — `session_event`, `flow_event`, `terminal_session` растут
   вечно. Решено не чистить: `flow_event` — история маршрута, и для карточек,
   заведённых до появления `Visited`, она единственная. Принятая особенность,
   не недосмотр.
2. **Схему невозможно эволюционировать**: `CREATE TABLE IF NOT EXISTS` на
   каждый старт — колонку в существующую таблицу добавить нечем. Предложение
   на будущее: лестница `PRAGMA user_version` (v0→v1 = текущий скрипт, дальше
   каждый шаг — ALTER'ы). В sources.db контракт «миграция может только
   добавлять» хотя бы записан комментарием, в acp.db — нет.
   *Обновление 2026-08-15: до релиза схема меняется прямо в CREATE TABLE (базы
   пересоздаются), а `migrate()` теперь штампует `PRAGMA user_version = 1` —
   первый пострелизный шаг делается той лестницей, не новым CREATE.*
3. `ClaimVCSEvent` — SELECT-потом-UPSERT без транзакции. Сегодня writer один,
   но то же выражается одним стейтментом:
   `ON CONFLICT ... DO UPDATE ... WHERE marker<>excluded.marker` +
   `RowsAffected` > 0 как признак «событие новое».
4. Инвариант «seq уникален внутри сессии» не выражен в схеме — индекс
   `idx_session_event_session` обычный. Он держится: seq — atomic в памяти,
   stale-сессии при рестарте только помечаются failed и к старым id событий
   никто не пишет. Индекс можно превратить в UNIQUE — с дедупом перед
   созданием на существующих данных.
5. `exit_code INTEGER NOT NULL DEFAULT 0` смешивает «ещё работает» и «вышел
   с 0»; различает `ended_at IS NULL`. Заметка — rebuild таблицы не окупается.
6. `SessionsForCard` — N+1 по событиям; один JOIN или IN закрыл бы.
7. В DSN стоит добавить `_synchronous=NORMAL` — рекомендованная пара к WAL;
   дефолтный FULL заметно медленнее на частых одиночных INSERT'ах событий.
8. Косметика: колонка `repo_path` против Go-поля `ProjectPath` (`flow_state`,
   `terminal_session`) — дрейф имён.

## sources.db

1. **`PruneEvents` — мёртвый код: его никто не вызывает.** Комментарий обещает
   «журнал ограничен, это диагностика, не архив», по факту журнал безлимитен.
   Единственная находка уровня «обещание в коде не выполняется». Вызывать
   после `AppendEvent` (раз в N вставок) или на старте менеджера.
2. Он к тому же **глобальный, а не per-source**: держит последние N строк
   всего журнала, так что болтливый источник вымывает журнал тихих — а
   читается журнал (`Events`) как раз per-source. При подключении переписать
   на окно по source.
3. `ForgetSource` — два DELETE без транзакции: упасть между ними значит
   оставить осиротевшие события.
4. То же отсутствие версионирования, что и в acp.db (там п. 2).
5. Косметика: mkdir `0o750` здесь против `0o755` в acp.

## Чего из чеклиста жанра здесь нет (и хорошо)

JSON-блобы только там, где содержимое действительно непрозрачно
(`payload_json`, `detail`), составные естественные PK, дефолты и NOT NULL на
месте. Отсутствие FK между acp/sources и карточками — не ошибка: `card_id`
живёт в другом файле БД, FK туда физически невозможен.

## При переработке: обобщить агентов

Агенты сегодня — ACP-специфичная сущность: реестр живёт в `config.json`
(`Agents []AgentEntry` в `internal/acp/config.go`), и вся модель принадлежит
пакету `internal/acp`. Если реестр при переработке переезжает в БД, заводить
его стоит сразу обобщённым: таблица `agents`, а не `acp_agents`, с колонкой
`type` — сегодняшние записи получают `type = "acp"`, а агент, говорящий по
другому протоколу, становится строкой с другим типом, а не второй таблицей
и второй веткой кода вокруг неё.

## Если решено применять

Приоритет по пользе: подключить `PruneEvents` (баг: обещание не выполняется) →
миграция 000041 (в первую очередь `file_info`) → `user_version`-лестница в
обоих сторах → DSN-строки → мелочи (`ClaimVCSEvent`, `ForgetSource` в
транзакции, N+1). Всё — маленькие независимые патчи, каждый объясним в один
абзац коммита.
